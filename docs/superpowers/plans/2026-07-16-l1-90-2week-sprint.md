# L1 90% 两周冲刺计划（Ollama + 规则 + 受限硬件）

> **状态**：草案，待逐步 dry-run 实证替换预估值
> **创建**：2026-07-16
> **关联**：`docs/superpowers/plans/2026-07-16-ollama-accuracy-90-93.md`（O1–O4 已落地）、`docs/VOC_V1.5_开发记录.md` R27

## Goal

在 **1–2 周**内把**近批次 L1** 从当前 dry-run 的 **84.6%** 提升到 **≥90%**，并尽量在连续批次上保持稳定；不重训 LoRA，不做全库 rewrite，所有改动先过 `eval_recent_rule_candidate.py` broken 门禁。

## 诚实的可行性判断（非承诺）

| 目标 | 概率 | 依据 |
|------|------|------|
| 单批 L1 达到 90% | **40–55%** | 头号错误集中（业务→非问题 68–75%），规则+Prompt 有明确抓手 |
| 连续 2 批（各 ≥200）稳定 90% | **15–25%** | 稳态需复核积累，原计划估 4–8 周 |

**基线事实：** 模型 `qwen2.5:14b-instruct-q4_K_M`（Ollama）；服务器 **36GB** 内存；近批次 84.6%（O1–O4 后，未部署）；全库 ~86%；训练集非问题 62–63.5% → 模型系统性偏向非问题；LoRA v2–v4 已失败，暂停。

## 硬件边界（36GB 内存）

| 模型 | 权重(q4) | 36GB 同机可行性 | 结论 |
|------|---------|----------------|------|
| 14B | ~9GB | 舒适 | **保持为默认分类模型** |
| 32B | ~19–20GB | 与后端/前端同机偏紧、延迟 2–3× | **仅低置信二次仲裁**，非默认 |
| 72B | ~40GB+ | 不可行 | 排除 |

**推论：** 硬件侧本冲刺**不换默认模型**；32B 只在软件杠杆吃满仍差 1–2pp 时，作为「低置信非问题样本」的第二意见（two-pass 仲裁），且需实测内存/延迟后再启用。真正的主战场是软件。

## 执行顺序与依赖

```
T0 部署已到手的 O1–O4（先把 +2.3pp 落地）
  → T1 反非问题规则扩展（最高 ROI）
  → T2 Prompt 决策边界纠偏（当天可测，有反噬风险）
  → T3 金标最近邻 few-shot（利用回流，助稳态）
  → T4 置信门控 two-pass（14B 严格复判；可选 32B 仲裁）
  → T5 MVP 门禁：连续 2 个 ≥200 批次验证
全程：每日 ~200 投喂 = 燃料 + 新错误池 + 验证批
```

每个 Task 完成后必须跑：
```bash
python3 performance_evaluation/eval_recent_rule_candidate.py \
  --since-days 7  --max-l1-broken 8 --max-l2-broken 3 \
  --export-csv performance_evaluation/exports/sprint_<task>_7d.csv
python3 performance_evaluation/eval_recent_rule_candidate.py \
  --since-days 30 --max-l1-broken 8 --max-l2-broken 3 \
  --export-csv performance_evaluation/exports/sprint_<task>_30d.csv
```
门禁：`L1 broken ≤ 8`、`L2 broken ≤ 3`、`L1 net > 0`。任一不过则收窄，不进下一步。

## Task 0：部署已通过的 O1–O4（第 1 天）

**目的**：让已验证的 +2.3pp 在**新批次**真实生效（dry-run 不改线上）。

**步骤**
1. 开发机：`./code_deploy/package_code.sh`
2. 传 `code_deploy/update.zip` + `.md5` 到服务器，`./code_deploy/update_server.sh`
3. 同步 `performance_evaluation/`（eval 脚本不在 zip 内）：`eval_recent_rule_candidate.py`、`post_rules_replay.py`、`evaluate_accuracy.py`、`time_utils.py`
4. 重启后端（`./start_ollama.sh` 或现有方式）

**验证**：服务器复跑 7 天 v5 命令，确认 `L1 after ≥ 84%`、`broken ≤ 8`。
**回滚**：`./code_deploy/rollback_server.sh`。

---

## Task 1：反「非问题」规则扩展（第 1–3 天，最高 ROI）

**目的**：吃掉头号错误（业务类→非问题，占 68–75%）。

**步骤**
1. 从近 30 天导出 `l1_change/error` 中「human=业务三类、model/replay=非问题」样本，按 human_l2 域聚类（充电 / 服务预约 / OTA / 车机 / 续航 / 交付 …）。
2. 对每个高频域，在 `classification_context_rules.py` 增加**确定性拉回规则**：含诉求/故障/服务流程/明确咨询请求 → 不得归非问题；纯表扬/闲聊/分享才保留非问题。
3. 复用现有 `apply_non_issue_guardrail` / guard 链，扩展 `_FORBID_NON_ISSUE` 等词表，不新增独立分支避免顺序冲突。
4. 每加一个域即 dry-run，broken 超门禁就立即收窄（参考 v1→v5 的收窄手法）。

**验证目标**：近批次 L1 再 `+2~4pp`；`L1 broken ≤ 8`。
**风险**：过宽会把真「非问题」拉成业务类 → 用 `_NEUTRAL_RANGE_INQUIRY` 等既有豁免兜底，双向核对 fixed/broken。

---

## Task 2：Prompt 决策边界纠偏（第 2–4 天，当天可测）

**目的**：从源头降低 14B 的非问题偏向。

**步骤**
1. 在分类提示词加入判定优先级 + 4–6 条 few-shot 反例（业务诉求即使语气平和也归业务三类）。
2. **提示词正文属禁改区** → 改前 git 打点，保留一键回滚。
3. 固定 temperature，确保可复现。

**验证目标**：`+1~2pp`；**必须双向 dry-run**，确认「非问题→业务类」假阳没有反超收益。不过则回滚。

---

## Task 3：金标最近邻 few-shot 检索（第 3–5 天，助稳态）

**目的**：用 4300+ 已复核金标动态压制偏向，且随复核量持续增益。

**步骤**
1. 对当前文本取「最相似的 3 条已复核样本」注入 prompt（复用内存金标缓存 + 现有 `historical_examples` 机制）。
2. 控制注入 token 预算，避免超 `num_ctx` 拖慢。

**验证目标**：`+1~3pp`；对「跨批次稳定」贡献最大（复核越多越稳）。

---

## Task 4：置信门控 two-pass（第 5–10 天，精度换延迟）

**目的**：对低置信非问题样本做严格复判。

**步骤**
1. 14B 输出 `l1=非问题` 且 `confidence < 阈值`（初设 0.6，按数据调）→ 用二分严格提示复判一次（仍 14B）。
2. 仅当 T1–T3 后仍差 1–2pp，再评估用 **32B 作仲裁**：
   - 先 `ollama pull qwen2.5:32b-instruct-q4_K_M`，实测 36GB 下内存峰值与单条延迟；
   - 内存/延迟不可接受则放弃 32B，只保留 14B 严格复判。

**验证目标**：`+1~2pp`；复判仅覆盖少数样本，日常吞吐（200/天）可接受。

---

## Task 5：MVP 门禁验证（第 10–14 天）

**步骤**
1. 连续 2 个独立批次，各 **≥200 条**，全部 Ollama 分类 + 人工复核（L1 必填，业务三类尽量填 L2）。
2. 每批跑 `eval_batch_accuracy.py` + `eval_recent_rule_candidate.py`。

**通过标准**：两批 **L1 ≥ 90%**、**L2 ≥ 82%**、broken 门禁全过。
**未通过**：按新错误池回到 Task 1，进入 Cycle 2（不强行上线）。

## 汇总：杠杆预期与风险

| 杠杆 | 预期 L1 | 风险 | 硬件需求 |
|------|--------|------|---------|
| T0 O1–O4 部署 | 已验证 +2.3pp | 低 | 无 |
| T1 反非问题规则 | +2~4pp | 过宽反噬 | 无 |
| T2 Prompt 纠偏 | +1~2pp | 假阳反超（禁改区） | 无 |
| T3 金标 few-shot | +1~3pp | token 预算/延迟 | 无 |
| T4 two-pass | +1~2pp | 延迟 | 可选 32B（36GB 偏紧） |

**不做**：1–2 周内不再赌 LoRA 重训（两轮失败）；不换默认模型（36GB 放不下 32B 常驻）；不做全库 `apply_post_rules_to_v3 --write`。

## 关键度量口径（勿混淆）

- **近批次**（7 天）：本冲刺主 KPI，规则/Prompt 直接反映。
- **近 30 天**：更稳的方向判断。
- **全库**：历史累计，replay 不自动改写，不作为冲刺日 KPI。

### 1.3b 阶段 0 盘点结果（2026-09-12 服务器实测）——**推翻两个原假设**

#### (a) 人工复核 L3 = 0 条

| 项 | 数值 |
|----|------|
| 已复核 | **8575** |
| **人工 `review_l3` 非空** | **0**（去重 0） |
| 模型 `v3_l3` 非空 | **9126** |

**结论：不存在"复核员填写的 L3 金标"。** 前端复核工作台从未采集 L3，8575 条复核里 L3 全空。
因此"人工三级标签"指的不是 `review_l3`，而是**人工标注体系文件** `label_project/label_hierarchy_final.json`。

#### (b) 人工体系 vs 聚类体系：重叠 99%，"融合"是伪命题

| 体系 | 文件 | L3 去重 |
|------|------|---------|
| 人工标注体系 | `label_hierarchy_final.json`（带 `频次`/`详情`） | **635** |
| 机器聚类体系 | `gold_l3_clusters_v3.json` | 492 |

| 交集情况 | 数量 |
|----------|------|
| 人工 ∩ 聚类 | **488** |
| 仅人工独有 | 147 |
| **仅聚类独有** | **4** |

**聚类体系几乎完全是人工体系的子集（492 中 488 个来自人工）。**
所以不需要"合并两套标签"——聚类的真实价值只有两项：**频次交叉校验**和**关键词匹配串**（后者需清洗）。

#### (c) 人工体系频次分布 → 约 150 个标签的具体落点

| 阈值 | 标签数 | | Top-N | 覆盖数据量 | 最低频次 |
|------|--------|---|-------|-----------|----------|
| 频次≥3 | 334 | | Top-100 | 70.4% | 14 |
| 频次≥5 | 224 | | Top-120 | 74.7% | 12 |
| **频次≥9–10** | **138–150** | | **Top-150** | **79.6%** | **9** |
| 频次≥20 | 80 | | Top-200 | 85.2% | 5 |

**取频次 ≥ 9 得约 150 个标签，覆盖约 80% 数据量**——与已定的「约 150 个」目标精确吻合。剩余 20% 走别名层或「其他-待归类」。

#### (d) 全局 Top-150 会压死体验需求类 → 必须分 L1 配额

| L1 | 人工 L2 | 人工 L3 去重 | L3/L2 | 全局 Top-150 中占位 |
|----|---------|-------------|-------|---------------------|
| 产品质量类 | 29 | 314 | 10.83 | **87** |
| 服务类 | 13 | 75 | 5.77 | **44** |
| 体验需求类 | **224** | 243 | **1.08** | **21** |
| 非问题 | 2 | 5 | 2.50 | **0** |

体验需求类有 243 个 L3，全局排序下只进 21 个。**必须按 L1 配额切分，不能用全局 Top-N。**

#### (e) 体验需求类层级错位（本次最大的结构问题）

- 人工体系「体验需求类」有 **224 个 L2**，但 `gold_l2_whitelist_v3.json` 只认 **24 个**
- `L3/L2 = 1.08` → 层级塌陷，L2 与 L3 近乎一对一
- 224 个 L2 中 **152 个频次 ≤ 2**，实例：`电池温度显示`(1)、`激光雷达软开关`(1)、`更多的氛围灯效果`(1)

这些"L2"本质是 **L3 级别的诉求点**，被错放在 L2 层。需独立任务下沉。

#### (f) 现有生产映射有效 → 收敛即可，**无需重建**

生产 `v3_l3` Top15 除 `通用` 外 **14/14 全部命中人工体系**（`闪充站问题`、`数字钥匙创建分享失败`、`Emira发动机故障`…）。

唯一突出问题：**`通用` 占 2056/9126 = 22.5%**，是最大的单点改进机会。

### 1.4 L3 生成链路（现状）

```
原文 → LabelMatcher
        ├─ 原体系规则 L3
        ├─ 金标聚类 canonical（keywords/synonyms 命中）
```

## 2. 硬件与模型升级建议

### 2.1 M5 Max 128GB 可用空间

统一内存 128GB，可供权重约 **90–96GB**（需给后端/前端/SQLite 留余量）。

### 2.2 核心思路转变：从「一个模型干所有活」到「按任务分配模型」

现状是 **同一个 14B 同时承担分类、L2 精排、L3 选择、汇报文案生成**。这是 36GB 内存下的妥协，
但这四件事的**要求完全不同**：

| 任务 | 频次 | 单次 token | 质量敏感度 | 延迟敏感度 |
|------|------|-----------|-----------|-----------|
| L1/L2 分类 | 200 条/天 × 每条 1 次 | 短（JSON 一行） | 中（有规则链兜底） | **高**（乘以 200） |
| L3 选择 | 同上 | 短 | 中 | 高 |
| 低置信仲裁 | 约 10–20 条/天 | 短 | **高** | 低 |
| **汇报洞察生成** | **1–4 次/周** | **长（1400 num_predict）** | **极高** | **极低** |

**关键洞察**：汇报洞察生成是「一周几次、每次都要拿给人看」的任务，质量敏感度最高、延迟最不敏感
——**它最该用大模型，却一直和分类共用 14B**。128GB 的最大价值不是把分类换成 32B，
而是**让汇报任务用得上 72B**。这直接服务于方向二「透视更多信息」的诉求。

### 2.3 按角色的模型分配（推荐方案）

| 角色 | 模型 | Q4 体积 | 常驻 | 理由 |
|------|------|---------|------|------|
| **分类主力**（L1/L2/L3） | **Qwen3-32B q4_K_M** | ~20GB | ✅ | ~28 tok/s；批量 200 条约 10–17 分钟 |
| **低置信仲裁** | Qwen3-72B q4 | ~43GB | ✅ | 每天仅 10–20 条，18 tok/s 完全够 |
| **汇报洞察生成** | Qwen3-72B q4（复用仲裁模型） | 共用 | ✅ | 一周几次，慢不要紧，质量优先 |
| **语义聚类**（§4.4 抱怨聚集） | `bge-m3` 嵌入模型 | ~1.2GB | ✅ | **新增能力**，见下 |
| 回滚 / 快速路径 | `qwen2.5:14b` q4 | ~9GB | 按需 | 保留，出问题立刻切回 |

**内存预算**：32B(20) + 72B(43) + bge-m3(1.2) ≈ **64GB 常驻**，在 90–96GB 可用空间内，
仍余约 26GB 给后端/SQLite/系统。**三个模型可同时常驻，无需反复加载卸载。**

需设置（否则 Ollama 会为省内存而卸载模型，导致每次调用都冷启动）：

```bash
export OLLAMA_MAX_LOADED_MODELS=3
export OLLAMA_KEEP_ALIVE=-1      # 常驻不卸载
export OLLAMA_NUM_PARALLEL=1     # 分类串行，避免争抢显存带宽
```

> `OLLAMA_KEEP_ALIVE=-1` 直接解决历史上「冷启动导致首批异常」的问题
> （见 `工作站每周运维与异常排查手册` §2 的 P1 冷启动条目）。

### 2.4 新增能力：嵌入模型（这是 128GB 才做得起的事）

方向二的「抱怨聚集」（§4.4）需要把散落在不同 L2 的同根因反馈聚到一起。
纯关键词做不到（"充电枪拔不出" 和 "地锁不降" 无共同词但同属充电桩体验），
需要**语义向量**。

| 项 | 说明 |
|----|------|
| 模型 | `bge-m3`（中文强、支持长文本）或 `qwen3-embedding` |
| 体积 | ~1.2GB，可长期常驻 |
| 用法 | 对每条原文算一次向量存库 → 周期性做层次聚类 → 簇内用 72B 起标题 |
| 增量成本 | 200 条/天的嵌入计算约几秒，可忽略 |
| 依赖 | 需在 `opinion` 表加一列存向量（或单独 `opinion_embedding` 表） |

**这项能力是方向二的技术前提**，建议与 32B 迁移同期落地。

### 2.5 不推荐的选项（明确排除）

| 选项 | 排除理由 |
|------|----------|
| 直接上 Qwen3-72B 做**分类主力** | 200 条 × 18 tok/s → 单批 25–35 分钟，且规则链是按 14B 调的，风险与收益不成比例 |
| 32B q8（~35GB） | 相比 q4 质量提升有限，速度明显下降；仅留作离线评估对照 |
| 235B MoE 类 | >100GB，挤掉其他模型，且吞吐不可接受 |
| 重启 MLX + LoRA 微调 | v2–v4 已失败并暂停；先把 32B 基线跑稳再谈微调 |

### 2.6 迁移必须过的门禁（不可跳）

换模型**不等于**准确率提升，必须实证：

```bash
# 1) 固定 holdout A/B（14B vs 32B），同一批文本
python3 performance_evaluation/ab_compare_models.py --baseline            # 现网基线
python3 performance_evaluation/ab_compare_models.py --candidate qwen3:32b # 候选推理
python3 performance_evaluation/ab_compare_models.py --compare             # 出对比

# 2) 近 7 天规则重放门禁（确认规则链未被新模型输出破坏）
python3 performance_evaluation/eval_recent_rule_candidate.py \
  --since-days 7 --max-l1-broken 8 --max-l2-broken 3

# 3) 新批次实证：连续 2 批各 ≥200 条
python3 performance_evaluation/eval_batch_accuracy.py --upload-batch <B1> --upload-batch <B2>
```

**通过标准**：holdout L1 **不回退**且 ≥ +2pp；`L1 broken ≤ 8`、`L2 broken ≤ 3`；单条延迟 ≤ 8s。
**未通过**：保留 14B，不换默认模型。

### 2.7 迁移顺序（每步都可独立回滚）

| 步 | 动作 | 风险 | 回滚方式 |
|----|------|------|----------|
| M-1 | 迁机器，仍用 14B，跑**一周同机基线** | 低 | — |
| M-2 | 加 `OLLAMA_KEEP_ALIVE=-1` 等常驻配置 | 低 | 删环境变量 |
| M-3 | **汇报洞察**切 72B（分类仍 14B） | **低**（不影响分类口径） | 改回模型名 |
| M-4 | 部署 bge-m3，仅算向量不改分类 | 低 | 停用嵌入 |
| M-5 | 分类 32B A/B → 过门禁才切默认 | **高** | 切回 14B |
| M-6 | 低置信 72B 仲裁 | 中 | 关仲裁开关 |

**M-3 是性价比最高、风险最低的一步**：只换汇报生成用的模型，完全不触碰分类口径，
却直接提升你最关心的汇报质量。建议机器到位后**优先做 M-3，不必等 M-5**。

### 2.8 风险提示（重要）

- **规则链是对 14B 输出调优的**。32B 的输出分布不同，O1–O4 / v4.2 的 guard 可能出现新的 `broken`。迁移期必须把 dry-run 门禁当硬门槛。
- **缓存键必须 bump**：`_cache_key` 已含 `QWEN_MODEL`，换模型自动失效，无需手工清缓存；但换 **prompt** 时仍需 bump `classify_v12_m4b_r4`。
- 建议**先升硬件、后换模型**，中间跑一周 14B 作为同机基线，避免「硬件+模型」两个变量同时变化导致无法归因。
- **模型分配需要代码改动**：当前 `qwen_ollama.py` 的分类与汇报共用 `VOC_QWEN_MODEL`。要实现按角色分配，需新增 `VOC_QWEN_MODEL_REPORT` / `VOC_QWEN_MODEL_ARBITER` 两个环境变量并在对应调用点读取。这是 M-3 的前置改动（改动小，但必须做）。

## 4. 方向二：汇报洞察升级（故障趋势 + 用户意图）

### 4.1 先定义清楚：「透视」和「提取」差在哪

你的诉求是"透视出更多信息，不是简单信息提取"。这两者的技术分界线很明确：

| | 信息提取 | **信息透视** |
|---|---------|-------------|
| 数据范围 | **单条记录内** | **跨记录 / 跨时间 / 跨维度** |
| 典型输出 | "这条是充电问题" | "充电问题里 38% 是同一批车主二次投诉，说明首次处理没解决" |
| 能否人工肉眼得出 | 能（看一眼原文就知道） | **不能**（要把上千条关联起来算） |
| 当前系统 | ✅ 已做到（L1/L2/L3） | ❌ 基本没有 |

**结论：现在汇报之所以像"信息罗列"，根因是所有分析都停留在「单条记录 + 按标签计数」这一层。**
要透视，必须引入**跨记录关联**。这才是方向二的核心，而不是把 LLM 提示词写得更花。

### 4.2 可用的透视维度（已核对数据库 schema）

`opinion` 表共 32 列，其中可用于跨维度关联的：

| 字段 | 透视价值 | 状态 |
|------|----------|------|
| **`vin`** | **同一台车反复投诉 → 首次未解决/真实复发**（最硬的信号） | ⚠️ 需查填充率 |
| **`phone`** | 同一车主多次反馈 → 未解决存量、情绪升级 | ⚠️ 需查填充率 |
| **`car_model`** | 故障是否集中在特定车型 → 指向硬件批次/设计问题 | ⚠️ 需查填充率 |
| `country` | 服务问题是否集中在特定市场 → 指向门店/服务商 | ⚠️ 需查填充率 |
| `source` | 渠道差异（不同渠道的问题结构） | 已有 |
| `create_time` | 时间序列、生命周期、时滞分析 | 已有 |
| `v3_l1/l2/l3` | 标签层级聚合 | 已有 |

> **⚠️ 前置动作**：`vin` / `phone` / `car_model` 的填充率决定了一半的透视能力能不能做。
> 见 §6.3 的盘点命令，**建议与「通用」取数一起跑**。
> 若 `vin` 填充率 < 30%，则复发分析退化为基于 `phone`，再退化为基于文本 `repeat_signal`。

### 4.3 架构原则：确定性字段在前，LLM 叙述在后

现在的问题是让 LLM 直接从原文"写洞察"，缺可校验的中间层 → 说服力不足且不可复现。

```
原文 → [单条结构化字段：意图/严重度/期望动作]      ← 可评估、可回溯
     → [跨记录透视：复发/聚集/生命周期/维度集中度]   ← 这一层是"透视"的本体
     → [LLM 只负责把已算出的结论写成人话]          ← 不让它做分析，只让它做表达
```

**LLM 不参与"发现"，只参与"表达"。** 所有结论都由确定性计算得出，LLM 拿到的是算好的数字，
这样汇报里的每一句话都能回溯到具体 SQL 和具体记录 —— 这是"能拿去汇报"的前提。

### 4.4 第一层：单条结构化字段（写入 `v3_label_meta`，不改现有键）

| 字段 | 取值（枚举，便于统计） | 说明 |
|------|------------------------|------|
| `intent` | 报障 / 求助 / 咨询 / 建议 / **投诉升级** / 表扬 / 告知 | **用户意图** |
| `expected_action` | 维修 / 上门 / 退款赔偿 / 解释说明 / 功能实现 / 无需动作 | 用户想要什么 |
| `severity` | 高 / 中 / 低 | 安全或车辆不可用 = 高 |
| `urgency` | 紧急 / 一般 | 含"催""多次""仍未解决" |
| `repeat_signal` | bool | "第N次""之前反馈过" → 文本层复发信号 |
| `root_cause_hint` | 短语（自由） | 供聚集分析，不做 KPI |

**落地方式**：优先规则（词表，可离线重放、零成本），LLM 仅补规则未覆盖的。与 O1–O4 相同的纯函数 + dry-run 模式。

**为什么这一层本身还不算透视**：它只是把单条信息结构化了。
但它是透视层的**输入**——没有 `intent`，就算不出"情绪升级率"；没有 `severity`，
就只能按条数排序，永远是"低危高频压过高危低危"。

### 4.5 第二层：跨记录透视指标（**这一层才是"透视"**）

以下每一条都是**单看任何一条记录都得不出、必须跨记录计算**的结论。

#### (1) 首次解决率 / 未解决存量 —— 按 `vin` 或 `phone` 关联

| 指标 | 算法 | 揭示什么 |
|------|------|----------|
| `repeat_rate` | 30 天内同一 `vin` 出现 ≥ 2 次的占比 | **首次处理没解决** |
| `unresolved_backlog` | 同 `vin` 最近一次仍为未处理状态的数量 | **积压的真实规模** |
| `mean_days_to_repeat` | 同 `vin` 两次反馈的平均间隔 | 处理时效 |

> 这是**最有说服力的透视指标**：它直接回答"我们的处理到底有没有用"，
> 而这个问题现在的汇报完全回答不了。

#### (2) 情绪升级迁移 —— `intent` 跨期对比

对每个 L2 算 `投诉升级 / (报障 + 求助)` 的比例，与上期对比。

比例上升 = **同样的问题，用户态度在恶化** —— 即使总条数没涨。
这是纯计数汇报完全看不见的信号，也是最容易在管理层汇报中"出彩"的一类结论。

#### (3) 期望未满足率 —— `expected_action` × 处理状态

| 指标 | 算法 |
|------|------|
| `unmet_rate` | 某 `expected_action` 下，`reflow_synced < 1` 或有复发的占比 |

揭示**用户想要的和我们做的之间的落差**。例如"要求上门"的未满足率远高于"要求解释说明"，
就指向上门服务资源不足，而不是某个具体故障。

#### (4) 维度集中度 —— 卡方 / 集中度检验

| 指标 | 算法 | 揭示什么 |
|------|------|----------|
| `model_concentration` | 某 L3 在各 `car_model` 上的分布是否显著偏离整体车型占比 | **指向特定车型的硬件/批次问题** |
| `region_concentration` | 某服务类 L2 在各 `country` 上的偏离度 | **指向特定市场的门店/服务商问题** |

这是从"有充电投诉"升级到"**充电投诉里 70% 来自某一款车，而该车只占保有量 20%**"的关键一步。

#### (5) 故障生命周期状态 —— 时间序列（详见 §4.6）

#### (6) 跨 L2 抱怨聚集 —— 语义向量（详见 §4.7）

#### (7) 时滞分析

某 L3 首次出现到形成规模的间隔天数；以及相对 OTA 发布日的时间分布
（若某故障集中在某次 OTA 后 7 天内爆发 → **直接指向该次 OTA**）。

> 需要 OTA 发布日期表作为外部输入，属可选增强项。

### 4.6 故障趋势：从「环比」升级为「生命周期状态」

当前 `detect_anomalies()` 只做一件事：本期 vs 过去 4 周期均值，超 1.5× 就报异常。
**问题是它只有"异常/不异常"两态**，分不清"新冒出来的"和"一直很高的"和"刚压下去又反弹的"。

对每个 (L2, L3) 组合计算状态：

| 状态 | 判定（建议初值，需实测校正） | 管理含义 |
|------|------------------------------|----------|
| **新发** | 过去 4 周期 = 0，本期 ≥ 3 | **要立刻看**，可能是新批次/新 OTA 引入 |
| **恶化** | 本期 ≥ 1.5× 前 4 期均值，且连续 2 期上升 | 正在失控 |
| **高位平台** | 连续 3 期在均值 ±20% 内且量级居 Top | **慢性病**，需专项而非应急 |
| **收敛** | 连续 2 期下降且本期 ≤ 0.6× 均值 | 措施有效，可作为成果汇报 |
| **复发** | 曾判定收敛后重回 ≥ 均值 | **措施无效或治标不治本** |

输出字段：`trend_state` + `weeks_active`（持续几期）+ `severity_weighted_count`。

**`severity_weighted_count` 很关键**：用 severity 加权（高=3/中=2/低=1）后排序，
避免"低危高频"（如"希望增加 APP 功能"）永远压过"高危低频"（如"行驶中动力中断"）。
这是现在按条数排 Top 问题的最大缺陷。

### 4.7 抱怨聚集：跨 L2 的同因聚合

现在只按 L2 分组，同一根因散落在多个 L2。真实例子（来自生产 L3 分布）：

```
充电体验这一个根因，散落在：
  产品质量类/LFC问题/闪充站问题        809 条
  产品质量类/LFC问题/家充桩问题        335 条
  产品质量类/车端充电问题/无法充电      149 条
  服务类/售后服务问题/…（充电桩报修）
→ 按 L2 看：四个互不相关的中等问题
→ 按根因看：一个超过 1300 条的头号问题
```

**这就是典型的"透视"：信息一直在数据里，只是被标签体系切碎了。**

做法（依赖 §2.4 的嵌入模型）：

1. 对每条原文算 `bge-m3` 向量
2. 在**跨 L2** 范围内做层次聚类（阈值控制簇数在 8–15）
3. 每簇用 72B 起一个标题 + 一句根因判断
4. 输出：涉及 L2 列表、条数、severity 分布、代表原文 3 条、`trend_state`

**降级方案**（嵌入模型未就绪时）：用 `root_cause_hint` + 标准 L3 做关键词共现聚类，
效果差但可先上线。

### 4.8 洞察模板库（保证"每期都有透视结论"）

不能指望 LLM 自由发挥就能产出洞察。做法是**预设一批分析假设，每期自动检验**，
命中就输出。每条模板 = 触发条件 + 输出句式。

| # | 触发条件 | 输出句式（数据自动填充） |
|---|----------|-------------------------|
| I1 | 某 L2 `repeat_rate` > 30% | 「{L2} 有 {x}% 是同一车辆二次反馈，首次处理未解决，建议复盘处理流程而非增加人力」 |
| I2 | 某 L2 投诉升级占比环比 +5pp 以上 | 「{L2} 总量持平但投诉升级占比从 {a}% 升至 {b}%，**用户耐心正在耗尽**」 |
| I3 | 某 L3 在某车型的占比 ≥ 整体占比 2 倍 | 「{L3} 有 {x}% 来自 {车型}，而该车型仅占总量 {y}%，指向车型特定问题」 |
| I4 | 出现 `trend_state = 新发` 且 severity 高 | 「本期新发高危问题 {L3}（{n} 条），过去 4 期为 0，建议立即排查」 |
| I5 | 出现 `trend_state = 复发` | 「{L3} 曾于 {期} 收敛后复发，前次措施未根治」 |
| I6 | 某 `expected_action` 的 `unmet_rate` 居首 | 「用户最常要求 {动作}（{n} 条），但未满足率 {x}%，是当前最大的期望落差」 |
| I7 | 某抱怨簇跨 ≥ 3 个 L2 | 「{簇标题} 横跨 {L2列表} 共 {n} 条，按现有标签口径被拆散，实际是单一根因」 |
| I8 | 某 L2 `trend_state = 高位平台` 且 weeks_active ≥ 4 | 「{L2} 已连续 {n} 期维持高位，属慢性问题，应转专项治理」 |
| I9 | severity 加权排序与条数排序 Top3 不一致 | 「按严重度加权后头号问题是 {A} 而非按条数的 {B}，建议调整资源投向」 |
| I10 | 某 L3 首现到规模化 < 7 天 | 「{L3} 在 {n} 天内从 0 升至 {m} 条，爆发速度异常，疑与近期变更相关」 |

**这个模板库是方向二的核心交付物。** 它的价值在于：
① 每期汇报必然有透视结论，不依赖 LLM 灵感；
② 每条结论可回溯到具体 SQL；
③ 可持续扩充（发现新的分析角度就加一条模板）。

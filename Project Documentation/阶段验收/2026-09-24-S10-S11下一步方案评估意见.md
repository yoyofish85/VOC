## 2. S10 评估：模型角色拆分 + 旧机 32B 离线预评估

### ✅ 合理

1. **前置角色拆分**：先加 `VOC_QWEN_MODEL_REPORT / VOC_QWEN_MODEL_ARBITER` 配置位，M-3 到货即可切 72B，不必临时改代码。
2. **不写生产**：32B 离线 A/B 只读、结果写 `state/ab_comparison_report.json`，生产分类保持 14B。
3. **门禁已在计划中**：固定 holdout(302) + 近 7 天 dry-run + 新批次，通过才换默认模型。

### ⚠️ 需补强（重点 4 条）

1. **holdout 有选择偏差（最需警惕）**：`baseline L1=90.07%（272/302）` 明显高于全库 `85.01%`，holdout 偏向易判样本 → **仅凭 holdout A/B 会偏乐观**。必须叠加「全库近 7 天 dry-run + 新批次连续 2 批 ≥200」双门禁，并在验收文案明示「holdout ≠ 全库」。

2. **32B 旧机独占是边界值**（约 22GB / 可用 25GB）：必须先小样本试跑确认不 OOM、不严重降速；**失败则放弃、等新机**，不硬撑。这一条是估算，不当既定事实。

3. **"汇报质量提升"缺客观验收**：换 72B 写汇报，若无 rubric，验收会沦为"感觉更好"。建议 S10 同步建立**人工盲评 rubric**（结论准确性 / 可读性 / 数字与依据一致 / 无编造），作为 M-3 的 A/B 验收标准。

4. **Ollama 版本兼容**：Qwen3-32B/72B 需要较新 Ollama，S10 前先确认旧机/新机 Ollama 版本，避免到货才踩坑。

### 🔧 实施细节提醒

- 角色拆分改造点是 `qwen_ollama.py`：当前分类与 `summarize_opinions` 共用 `VOC_QWEN_MODEL`，需在**分类调用点与汇报调用点分别**读对应变量；建议补"汇报模型切换"单测，避免只覆盖分类路径。
- 确认 `ab_compare_models.py --candidate qwen3:32b` 能正确落盘并与 14B baseline 对比（baseline 已在 09-12 生成）。

## 3. S11 评估：新机迁移（M-1 → M-6）

### ✅ 合理

迁移顺序「14B 一周同机基线 → 常驻配置 → M-3 汇报 72B → M-5 分类 32B → M-6 仲裁」每步独立回滚，正确。

### ⚠️ 需补强

1. **M-3（汇报切 72B）应优先做、不必等 M-5**：最低风险、最高汇报质量收益，且不触碰分类口径——建议新机到位后第一优先。
2. **常驻配置要防"汇报/仲裁"与"分类"争抢内存带宽**：`OLLAMA_NUM_PARALLEL=1` 对分类串行正确，但 72B 汇报是长任务，应安排在非分类时段，或明确与分类模型分时/并行策略。
3. **128GB 内存预算预留**：32B(20) + 72B(43) + bge-m3(1.2) ≈ 64GB 常驻，还需留 KV cache；S8 的 `opinion_embedding.db` 向量库要随 S11 一并迁移到新机。
4. **先硬件后模型、同机基线不可省**：避免「硬件 + 模型」双变量无法归因。

## 8. L3 生产落地：必须提上日程（补充，2026-09-24）

### 8.1 关键发现：L3「消化通用」实际未达标

S3/S4/S5 只是「定版 + 开发机 dry-run 通过」，生产开关 `VOC_L3_STANDARD_V1` **默认关闭、尚未上线**。

dry-run 实测（400 条「通用」样本，dev 与 server 一致）：

| 指标 | dev | server |
|------|-----|--------|
| 改造前「通用」占比 | 100% | 100% |
| 改造后「通用」占比 | 0% ✅ | 0% ✅ |
| **改造后「其他-待归类」占比** | **61.5%** ⚠️ | **64%** ⚠️ |
| **真正命中标准 L3 占比** | **38.5%** ⚠️ | **36%** ⚠️ |

**结论**：61.5% 的「通用」没被消化，只是从「通用」改名成「其他-待归类」。总表里「T99 占比偏高」的根因即此——不是 UI 问题，是 **214 标准层 + 303 别名对生产存量文本的实际覆盖仅约 36–38%**。`gate_ok=true` 只证明 L1/L2 不回退，**不证明「通用 ≤12%」目标达成**（实际"待归类"反而高于原"通用"）。
